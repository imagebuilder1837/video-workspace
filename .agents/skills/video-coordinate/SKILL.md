# 复杂项目协调

借用通用 `/implement-spec` 的任务图、新上下文与集成机制；制作使用视频能力。主代理负责调度、集成与共享资料。

## 前提

1. 明确目标项目、本次授权范围，读取当前设计、相关票及讨论、本地指引。必须已提供 tracker 和项目自己的 Git；缺配置提示先运行 `/video-setup`。
2. 核对 Git 根目录确为目标项目，已有可用提交且工作区干净；否则说明并暂停，按明确授权处理基线或未提交修改。Git 外素材与视频仍按 [项目约定](../video-produce/references/project-layout.md) 留存。
3. 首次调用子代理前读取实际配置与能力，按任务选择执行者。缺少所需隔离／执行能力或启动失败时报告阻塞。

## 派发与集成

1. 从当前制作基线建立集成分支，按任务依赖派发已就绪的工作；本地票遵循 [tracker 约定](../video-tasks/references/issue-tracker.md)。需要额外拆分时先用 `/video-tasks` 确认粒度。
2. 每个执行子代理使用新上下文，尽可能后台运行。修改版本化制作文件的任务默认使用基于集成分支的独立分支／worktree。并行写入者须隔离，隔离受阻时报告阻塞。
3. Brief 提供工作台与实际执行目录、当前设计／任务、必要素材及能力的可解析指针，并说明相关意图、已确认视听约束、可改范围、预期产物和验收要求。共享设计的写入责任见 [设计与执行](../video-produce/references/project-layout.md#设计与执行)。制作复用 `/video-produce`，问题驱动原型复用 `/video-prototype`。
4. 执行目录先核对原项目 Git 外输入和共享链接的可达性，按 [本地文件](../video-produce/references/local-files.md) 取用。执行者仅提交本票版本化改动，返回分支／提交、实际产物、所做检查与未知、阻塞及交付／handoff 路径。
5. 主代理优先用确定性命令合并，仅在语义冲突时调用合并子代理。集成成功后更新状态并派发新就绪任务，需要实际判断／检查结论的依赖仍须取得该交付。与集成分支的机械同步在任务分支处理，保留用户及其他任务改动。

## 统一审查与修正

1. 本次范围的任务集成后，派一个独立新上下文子代理使用 `/video-review`，对照当前设计、任务验收条件和实际集成结果统一核查。提供正确的源码状态及实际预览／导出，必要取证可由该子代理完成。
2. 只审查一轮。发现授权范围内的问题时，交给一个新的执行子代理集中修正、提交，再由主代理集成；小修正沿用受影响原票。需要改变关键创作选择的问题先转 `/video-discuss`。
3. 修复集成后交给人查看。票与交付说明区分已审对象、修复者报告的处理、修复后未复审和待人工判断事项。

## 设计变化

采纳改变设计的反馈后，主代理在唯一设计正文同步实际受影响内容，更新相关票与依赖，通知、调整或停止受影响的执行者；未受影响工作继续保留。取消票保留原因，晚到结果按当前设计核对后决定集成。

## 交付与清理

1. 返回集成分支／提交、实际产物及范围、一轮审查发现、修复情况、未检查与待人工判断内容。
2. 保存子代理交付／handoff 路径。清理前将必要依赖、Git 外产物与证据留在正式项目适用位置，明确实际文件。
3. 使用 `worktree.discard` 清理本轮创建的执行 worktree。失败或中断先报告并保留恢复所需内容。

人工跨会话接续见 [跨会话接续](../video-produce/references/project-layout.md#跨会话接续)。
